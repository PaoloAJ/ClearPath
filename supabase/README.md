# Supabase

The database side of ClearPath: schema, security rules, trust-rule RPCs, demo mode, and the seeded demo zone. Owned by the data workstream ([AGENT3](../agents/AGENT3.md)). Contracts other lanes rely on are listed in [AGENTS.md → Contracts](../AGENTS.md#4-contracts).

| Path | What |
|---|---|
| `migrations/` | Schema, RLS, grants, RPCs. Append-only: never edit a merged migration. |
| `seed.sql` | Generated by `data/campus/import.ts`. Never edit by hand. |
| `tests/*.test.sql` | pgTAP tests, run by `supabase test db` and CI |
| `scripts/smoke.mts` | HTTP smoke test of the API the app uses (local or hosted) |

## Local workflow

```bash
supabase start            # Postgres, PostgREST, Realtime, Storage in Docker
make seed                 # GeoJSON + samples.json → seed.sql → supabase db reset
supabase test db          # pgTAP tests
eval "$(supabase status -o env | sed 's/^/export /')" && pnpm tsx supabase/scripts/smoke.mts
```

`supabase db start` (database only) is enough for `supabase test db`. The smoke test needs the full `supabase start`.

## Settings

Trust-rule thresholds and the demo switch live in one row, `private.app_settings`. Clients can't read or change it. Change it in the SQL editor:

| Column | Default | Used by |
|---|---|---|
| `alert_ttl` | `4 hours` | `report_alert`, `vote_alert` ("still there"), `demo_*` |
| `cleared_votes_to_resolve` | `2` | `vote_alert` |
| `report_radius_m` | `15` | `report_alert`, `demo_inject_alert` (polygon buffer) |
| `report_max_distance_m` | `100` | `report_alert` (how far from a mapped path a report may land) |
| `demo_enabled` | `false` (`true` after `make seed`) | every `demo_*` RPC |

```sql
update private.app_settings set demo_enabled = true;   -- before a presentation
update private.app_settings set demo_enabled = false;  -- after
```

## Hosted setup

Do this with AGENT4 once the Clerk application exists. Every step is needed: the app can't sign in until steps 2 and 3 are done.

1. **Create the Supabase project.** Note the project ref, API URL, and anon key. They go into `apps/mobile/.env` (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`), and the pooled connection string goes into `services/routing/.env` (`DATABASE_URL`).
2. **Connect Clerk.** In Clerk, activate the Supabase integration. That adds `role: authenticated` to session tokens. Keep the custom claim named `app_role` (README → Set up Clerk). In the Supabase dashboard, go to **Authentication → Third-party auth → Add Clerk** and enter the Clerk domain.
3. **Use the same domain locally.** In `config.toml`, set `[auth.third_party.clerk] enabled = true` and `domain` together. With a placeholder domain the CLI won't start (see Gotchas).
4. **Push the schema.**
   ```bash
   supabase link --project-ref <ref>
   supabase db push
   ```
5. **Load the demo zone once.** The graph (nodes, edges, elevators) and the sample state live in `seed.sql`, which `db push` skips unless you ask:
   ```bash
   supabase db push --include-seed
   ```
   The seed truncates alerts, votes, and elevator reports before loading. Only run it on first setup, or when the graph changes and wiping live alerts is acceptable. It also turns demo mode on. Turn it off afterward unless a presentation is coming.
6. **Mark facilities accounts.** In Clerk, set `public_metadata.role = "facilities"` on accounts that post verified alerts.
7. **Smoke-test it.** Get a session token from the app in development (log `await getToken()`), then run:
   ```bash
   API_URL=https://<ref>.supabase.co ANON_KEY=<anon key> TOKEN=<session token> pnpm tsx supabase/scripts/smoke.mts
   ```
   That run is read-only. `--write` also exercises reports, votes, elevator status, and the demo RPCs, and it **ends with `demo_reset()`, which replaces every alert with the sample state.** Only use `--write` on a project that's in demo mode with nothing to lose.

## Gotchas

- **Clerk domain is fetched at startup.** With `[auth.third_party.clerk] enabled = true`, the CLI fetches `https://<domain>/.well-known/openid-configuration` and refuses to start if that fails. Placeholders break `supabase start` locally and the Database check in CI.
- **API roles start with no table access.** Supabase versions disagree on default grants, so `20261030042627_rls_policies.sql` revokes everything from `anon` and `authenticated`, including default privileges for future tables, then grants back exactly what the app uses. **A new table needs explicit grants in its migration,** or the app can't see it.
- **JWT `role` is reserved.** Supabase picks the Postgres role from it. Ours is `app_role` (`public.is_facilities()`).
- **API sessions run `pg_safeupdate`.** An `update` or `delete` without a `where` clause fails when it runs through PostgREST, even inside a `security definer` function. Write `where true` when you mean every row (see `private.apply_demo_samples()`).
- **Storage blocks direct SQL deletes.** Test storage policies by inserting into `storage.objects`, and check delete rules by inspecting `pg_policies`. The smoke test covers the Storage HTTP API itself (size limit, MIME types, folders).
- **PostgREST returns geography as WKB.** The app reads alerts through `alerts_feed`, which returns GeoJSON and a center point.
